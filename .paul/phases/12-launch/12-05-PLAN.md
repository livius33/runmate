## The cancellation form (finding 3)

§ 312k BGB wants the cancellation reachable without signing in, so the form stays public. A confirmation mail
would be the obvious guard, but no mail provider is chosen (12-07). What this plan builds works without mail:

- The first request for an account is carried out as today: cancellation at the end of the paid period, never
  immediately. Nothing is lost until then.
- A signed-in owner sees it in the settings ("Dein Plus endet am …") and can take it back with one button
  (Paddle: remove the scheduled change).
- After a take-back, further requests through the public form for that account are not carried out for 90 days.
  They are stored and shown to the signed-in owner, who confirms or discards them.
- At most one request per account in 24 hours is processed; the answer of the form never differs.
- The log line of every request carries the user id and the subscription id.

Open for Livius (does not block the build): whether the AGB should say that a cancellation through the form is
confirmed by e-mail to the account's address. Once 12-07 has a mailer, every request also sends that mail.
</context>

<acceptance_criteria>
AC-1  Form request for an account with a live subscription: scheduled at period end, visible in the settings,
      reversible there. Second request inside 24 hours: no Paddle call. Request after a take-back: stored, no Paddle
      call, owner can confirm or discard. The HTTP answer is identical in all cases and for unknown addresses.
AC-2  No checkout can be opened while the account has a live subscription or a checkout was started in the last
      15 minutes (server refuses the signature; the buttons follow).
AC-3  An event for a subscription id other than the stored live one does not replace the row; the second id is
      kept, logged with both ids, and cancelled by "cancel" and by account deletion as well.
AC-4  Account deletion: a failed Paddle cancel is retried, and if it still fails the subscription id and customer
      id are logged and kept with the tombstone, so it can be cancelled later.
AC-5  Checkout is offered only when price ids, client token, API key and webhook secret are all set and
      `PADDLE_ENV` is exactly `sandbox` or `production`; otherwise one clear line in the log at start-up.
AC-6  `unknown-user` events are logged at error level with event id and subscription id. A daily job compares
      every non-final subscription row with Paddle and applies the difference.
AC-7  The webhook's read-modify-write and the go-live of a draft are safe against two concurrent requests.
AC-8  An address that already used a trial does not get a second one after deleting the account, if the tombstone
      allows telling (it stores a hash, never the address). If it does not, report instead of adding personal data.
AC-9  `npx tsc --noEmit`, `npx vitest run` and `npm run build` are green; every AC has a test.
</acceptance_criteria>
